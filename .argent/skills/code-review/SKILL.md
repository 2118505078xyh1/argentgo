# 代码审查方法论

目标：在最小上下文中找出真实缺陷，并按风险排序交付。审查是**只读诊断**，默认不修改代码。

## 第一步：确定审查范围

- 明确要审的是一次 diff、一个文件还是一个模块；用 `git status` / `git diff` 或工具读取**实际改动**，不要凭记忆。
- 阅读改动周围至少一层上下文（调用方、被调用方、类型定义），确认意图。
- 若改动附带需求或 issue 描述，先对齐"应该做什么"，再判断"实际做了什么"。
- 范围过大时先说明分几块审查，不要跳跃式浏览。

## 第二步：分维度检查（逐项过，不要只看第一眼）

1. **正确性**：逻辑是否实现了意图？条件、比较、运算符、顺序、状态转换是否反了或漏了？返回值的语义是否与调用方契约一致？
2. **边界与输入**：空值、nil、零长度、极值、单元素、重复元素、超长输入、Unicode/多字节、时区与编码。循环是否可能不进、多进一次或越界？
3. **并发与时序**：共享状态是否加锁？锁顺序是否一致（死锁）？是否有数据竞争、丢失更新、ABA、竞态条件？context 取消后是否还能访问已释放资源？goroutine/闭包是否捕获了循环变量？
4. **错误处理**：错误是否被吞掉、被覆盖、包装时是否丢失（`%w`）？失败路径是否留下半初始化状态？是否提供哨兵错误供 `errors.Is` 匹配？重试是否幂等？
5. **资源与性能**：文件、连接、锁、计时器、goroutine 是否成对释放（含错误路径与 panic 路径）？是否有循环内 O(n²)、无界缓冲、重复分配或泄漏？热路径是否引入锁竞争或额外分配？
6. **安全**：路径是否解析到工作区内（`..` / 绝对路径逃逸）？输入是否被校验/转义（注入、命令执行）？脱敏是否发生在写日志**之前**？权限与审批链是否可绕过？
7. **可测性**：改动是否可被单测覆盖？是否依赖真实网络、时间、随机数或全局状态而无法注入？是否缺少失败路径测试？

> 对每个维度，先问"这里有没有问题"，再问"问题在什么条件下触发"。凡是没有触发条件的怀疑，降级为疑问而非缺陷。

## 第三步：严重度分级

| 级别 | 含义 | 例子 |
|---|---|---|
| **Blocker** | 导致数据丢失、崩溃、安全漏洞，上线必须阻断 | 路径逃逸、吞掉认证错误、竞态导致数据错乱 |
| **Major** | 常见条件下功能错误或资源泄漏 | 边界条件算错、错误分支泄漏连接、锁顺序不一致 |
| **Minor** | 不影响主流程但有隐患或明显偏差 | 错误信息不清、缺一个边界测试、轻微性能退化 |
| **Nit** | 风格、命名、注释、格式 | 命名不一致、拼写、冗余注释 |

分级必须附带**触发条件**；"可能有问题"不是 Blocker。

## 第四步：输出

1. **先报最严重的 3 个问题**：按严重度降序，每个包含——位置（文件:行号）、触发条件、影响、建议修法。若还有更多，用一行写"其他 N 项，最高级别为 X"，不展开。
2. **区分事实与推测**：能指出具体代码路径的是事实；只能说"也许"的明确标注为待确认，并给出验证方法。
3. **肯定做对的地方**（1-2 句），避免通篇否定。
4. **默认不改代码**。只有用户明确要求"顺手修一下"或"直接改"时才动代码，且一次只修一个已确认的问题，修完说明改了什么。
5. 末尾给出结论：可以合并 / 修复 Blocker 后合并 / 不建议合并。

## 禁止

- 不把风格偏好当成 Major 以上问题。
- 不报告没有触发条件的"潜在问题"来充数。
- 不在审查中悄悄重构、格式化无关代码或"顺手"修 bug。
- 不把"已写出审查结论"当作"已验证修复"——修复需要单独的测试确认。
