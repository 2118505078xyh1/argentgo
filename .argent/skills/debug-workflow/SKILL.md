# 调试工作流

目标：用可重复的实验把"猜测"收敛到"根因"，再做最小修复。每一步都要留下可验证的证据。

## 硬规则（违反即停止）

1. **不凭猜测改代码。** 没有复现和证据之前，禁止修改生产代码。
2. **一次只改一个变量。** 同时改两处就无法判断哪一处起作用。每次实验只改变一个条件，其余保持不变。
3. **禁止顺手重构。** 排查期间不改格式、不重命名、不"优化"无关代码——这些改动会污染 diff 并引入新变量。
4. 临时插桩（日志、断言）在定位完成后必须拆除，除非它本身是有价值的长期诊断。

## 阶段

### 1. 复现（Reproduce）

- 拿到**确切的输入与确切的期望/实际输出**。没有最小复现，不进入下一阶段。
- 写下可重复的执行命令或测试；优先用自动化测试固化复现，它同时成为后续回归测试。
- 记录环境：版本、配置、平台、相关依赖。若"有时会发生"，先找出影响它的那个条件（时间、顺序、并发、数据）。
- 复现成功前，不写任何"修复"。

### 2. 假设（Hypothesize）

- 基于证据列出**可证伪**的假设，按可能性排序。每条写清"如果它成立，我应该观察到什么"。
- 假设要具体：不说"并发问题"，而说"两个 goroutine 同时写 `counter` 且未加锁，导致计数丢失"。

### 3. 证伪（Falsify）

- 设计能**推翻**假设的实验，而不是只找支持它的证据。
- 每次只验证一个假设、只改一个变量：加一条日志、打印一个中间值、固定一个随机种子、串行化一段并发。
- 观察结果并更新假设列表：被推翻的划掉，剩下的重新排序。不要因为"我觉得是它"就跳过验证。

### 4. 根因（Root cause）

- 找到能**完整解释所有已知现象**的那条原因，包括"为什么以前没暴露"。
- 区分直接原因与根本原因：空指针是现象，"调用方未处理错误返回就继续使用 nil"才是根因。
- 能回答"改哪里能让这一类问题都不再发生"，才算找到根因。

### 5. 最小修复（Minimal fix）

- 只改根因所需的最小范围，不顺带修改无关代码。
- 修复要与项目既有范式一致（错误用 `%w` 包装、路径校验走安全链等）。
- 若修复涉及多个改动点，逐项说明每一点对应哪条证据。

### 6. 回归测试（Regression test）

- 把第 1 步的最小复现变成一条会失败的测试，确认它在修复前失败、修复后通过。
- 测试覆盖触发条件与边界，不联网、不依赖真实时间/随机数。
- 跑相关包的完整测试，确认没有引入新失败。

### 7. 解释（Explain）

- 用一段话说清：现象 → 根因 → 为什么这个修复有效 → 如何验证。
- 说明留下或拆除的插桩，以及需要用户注意的后续动作（数据修复、监控告警等）。

## 卡住了怎么办

- 超过 3 个假设被推翻：回到第 1 步，检查复现是否真的稳定、是否漏了条件。
- 只在生产环境出现：在测试环境补齐相同的配置/数据/并发条件，而不是直接在生产上试改。
- 不要用"先改了看看"代替证伪——那只会把一个问题变成两个。
