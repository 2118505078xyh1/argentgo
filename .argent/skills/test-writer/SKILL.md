# 补测试方法论

目标：用尽量少的测试，锁住尽量真实的失败可能。测试不是为了满足覆盖率数字，而是为了让未来的改动在破坏行为时**自动报警**。

## 第一步：确定测试边界

- 明确被测单元：一个函数、一个方法还是一段端到端流程？优先在最小的可注入边界上测试。
- 列出这次改动的**行为契约**：输入 → 输出/副作用，包括错误返回与状态变化。
- 依赖真实时间、随机数、网络、文件系统或全局状态时，先找到注入点（接口、函数字段、参数），不要直接连真实资源。

## 第二步：列出必须覆盖的四类用例

1. **正常路径**：典型输入，验证返回结果与可观察副作用。一个用例即可，不要重复。
2. **边界与极值**：空/nil、零长度、单元素、恰好边界值、超长输入、多字节/Unicode、重复项。循环相关要覆盖"不进循环""只进一次""进出多次"。
3. **错误路径**：每个 `return err` 分支、每个被拒绝的输入、每个失败的下游调用。验证错误**确实非 nil**，必要时用 `errors.Is` 验证哨兵错误；同时验证失败后没有留下半初始化状态或资源泄漏。
4. **回归用例**：这次修复的 bug 本身。先写测试证明它在修复前失败，再让它随修复通过——这是防止复发的唯一可靠方式。

> 不要为"代码长这样"写测试，要为"行为应该怎样"写测试。断言结果，不断言实现细节。

## 第三步：写法的硬约束

- **表格驱动**：同类用例合并为一个表驱动测试，每行给出 `name`、输入、期望。测试名要体现行为，如 `TestEditRequiresUniqueMatch`。
- **不联网**：不调用真实 API、不访问外部服务。用 fake/stub 注入依赖；短小的 helpers 放在测试文件内。
- **不依赖真实时间与随机数**：固定时间源与随机种子，或直接注入。
- **测试与源码同目录**：使用同一 package（需要时用 `xxx_test` 外部包）以验证对外契约。
- **确定性**：同一输入每次得到同一结果；不依赖执行顺序、时区或机器状态。
- **断言要有信息量**：失败信息写清输入与期望/实际，用 `%q`、`%#v`。

## 第四步：评审自己的测试

- 变异检查：若把生产代码的那行逻辑改错或删掉，这条测试会失败吗？不会，就是无效测试。
- 检查是否过度指定：断言了不该关心的顺序或内部调用次数，会让未来的重构误报。
- 检查清理：临时目录用 `t.TempDir()`，启动的 goroutine/服务要能被取消并等待退出。
- 运行 `go test ./...` 与（热路径的）`go test -race` 确认全绿；基准测试的断言同样要成立。

## 输出

说明：新增了哪些测试、各自锁定哪类行为、为什么这些用例足以覆盖本次改动的风险；如有未覆盖的角落，明确指出并说明取舍。
