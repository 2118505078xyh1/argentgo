根据当前工作区的改动生成一份 PR 描述草稿。用户参数：$ARGUMENTS

## 1. 收集信息

- 用 `git status --short`、`git diff --stat` 看改动范围；必要时用 `git log --oneline -5` 看近期提交风格。
- 若已相对目标分支建立差异，用 `git diff <base>...HEAD --stat` 确认本次 PR 真正包含的内容。
- 阅读关键 diff，提炼**变更意图**，不要逐行复述补丁。

## 2. 生成 PR 描述

按以下结构输出（中文，简洁）：

### 标题

一行，与项目提交风格一致（conventional commit 风格优先），概括本次变更。

### 动机 / 背景

为什么做这个改动，解决了什么问题或痛点。$ARGUMENTS 中提供的背景优先采信。

### 主要变更

- 分点列出 3-6 项，按"做了什么 + 为什么"写，而不是按文件罗列。
- 指出行为变化、接口变化或配置变化。

### 验证方式

- 列出运行过的命令（如 `go test ./...`、`go vet ./...`、`gofmt -l .`）及其结果。
- 说明手工验证步骤（如适用）。

### 风险与注意事项

- 可能的兼容性影响、需要 reviewers 特别关注的地方、待办或后续跟进。
- 没有则写"无"。

## 3. 交付

- 把草稿完整展示给用户，允许其修改。
- **不自动创建 PR、不 push 分支**，除非用户在参数或后续确认中明确要求。
- 若信息不足（例如看不出动机），明确列出需要用户补充的问题，而不是编造背景。
